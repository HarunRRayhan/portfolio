<p>Most developers know not to commit a <code>.env</code> file. It goes into <code>.gitignore</code>, CI gets its own secrets, and anyone who pastes one into Slack gets a polite lecture.</p>

<p>Then the same team leaves <code>terraform.tfstate</code> on a laptop, copies it into a CI artifact, or gives every developer read access to the production state bucket.</p>

<p>That file deserves at least as much care as <code>.env</code>. Sometimes more.</p>

<p>Terraform state can contain database passwords, generated access keys, private key material, connection strings, and values returned by data sources. Even when there are no credentials in it, state is a detailed map of the account: resource names, ARNs, network IDs, endpoints, roles, and relationships.</p>

<p>The dangerous part is that Terraform makes sensitive values look safer than they are.</p>

<h2><code>sensitive = true</code> hides output, not data</h2>

<p>Consider a normal sensitive variable:</p>

<pre><code class="language-hcl">variable "hrr_database_password" {
  type      = string
  sensitive = true
}

resource "aws_db_instance" "hrr_app" {
  identifier = "app-production"
  username   = "app"
  password   = var.hrr_database_password

  # Other RDS settings omitted
}</code></pre>

<p>Marking the variable as sensitive stops Terraform from printing its value in the usual CLI and HCP Terraform output. It does not automatically remove the value from state.</p>

<p>Terraform needs resource attributes so it can compare the configuration with the real resource later. The state snapshot is JSON, and many providers store sensitive arguments there. HashiCorp says this directly in its <a href="https://developer.hashicorp.com/terraform/language/manage-sensitive-data">sensitive data documentation</a>: <code>sensitive</code> values are redacted in output, while state access still needs to be controlled.</p>

<p>This distinction is easy to miss:</p>

<ul>
  <li><strong>Sensitive</strong> means “do not display this in normal output.”</li>
  <li><strong>Ephemeral</strong> means “do not store this in state or plan files.”</li>
</ul>

<p>Those are different promises.</p>

<h2>What I assume is inside every state file</h2>

<p>I treat a state snapshot as if it contains credentials, even when I think the configuration only creates harmless infrastructure.</p>

<p>That assumption holds up better than checking the file once and declaring it clean. Providers change. Modules add outputs. A resource that stored only an ARN last month may gain a password argument next month. Someone may read a secret through a data source while debugging and forget that Terraform recorded the result.</p>

<p>A production state file commonly exposes some mix of:</p>

<ul>
  <li>database usernames and passwords passed through resource arguments</li>
  <li>IAM access key secrets created by Terraform</li>
  <li>private keys generated by the TLS provider</li>
  <li>API tokens and webhook URLs passed into services</li>
  <li>internal hostnames, subnet IDs, security groups, and account IDs</li>
  <li>Lambda environment variables and application configuration</li>
</ul>

<p>Not every resource stores every value. Provider schemas decide that. I don't use that uncertainty as a security boundary.</p>

<h2>My minimum S3 backend</h2>

<p>For AWS projects, I usually keep state in a dedicated S3 bucket. The bucket isn't shared with uploads, logs, or application assets. Its only job is holding Terraform state.</p>

<p>This is the backend configuration in the application stack:</p>

<pre><code class="language-hcl">terraform {
  required_version = ">= 1.10.0"

  backend "s3" {
    bucket       = "example-terraform-state"
    key          = "payments/production/terraform.tfstate"
    region       = "us-east-1"
    encrypt      = true
    kms_key_id   = "arn:aws:kms:us-east-1:123456789012:key/REPLACE_ME"
    use_lockfile = true
  }
}</code></pre>

<p><code>use_lockfile = true</code> turns on native S3 state locking. It requires Terraform 1.10 or newer. Older setups often use a DynamoDB table for locking, but that mechanism is now deprecated. New projects don't need the extra table.</p>

<p>Locking is not encryption. It prevents two applies from writing the same state at once. Without it, two correct changes can still leave one broken state snapshot.</p>

<p>I create the backend bucket in a small bootstrap stack, separate from the application. The important parts look like this:</p>

<pre><code class="language-hcl">resource "aws_s3_bucket" "hrr_terraform_state" {
  bucket = "example-terraform-state"

  lifecycle {
    prevent_destroy = true
  }
}

resource "aws_s3_bucket_versioning" "hrr_terraform_state" {
  bucket = aws_s3_bucket.hrr_terraform_state.id

  versioning_configuration {
    status = "Enabled"
  }
}

resource "aws_s3_bucket_server_side_encryption_configuration" "hrr_terraform_state" {
  bucket = aws_s3_bucket.hrr_terraform_state.id

  rule {
    apply_server_side_encryption_by_default {
      sse_algorithm     = "aws:kms"
      kms_master_key_id = aws_kms_key.hrr_terraform_state.arn
    }

    bucket_key_enabled = true
  }
}

resource "aws_s3_bucket_public_access_block" "hrr_terraform_state" {
  bucket = aws_s3_bucket.hrr_terraform_state.id

  block_public_acls       = true
  block_public_policy     = true
  ignore_public_acls      = true
  restrict_public_buckets = true
}

resource "aws_kms_key" "hrr_terraform_state" {
  description             = "Encrypt Terraform state"
  enable_key_rotation     = true
  deletion_window_in_days = 30

  lifecycle {
    prevent_destroy = true
  }
}</code></pre>

<p>S3 already encrypts new objects with SSE-S3 by default. I use a customer-managed KMS key here because it gives me a second permission boundary and an audit trail for key usage. It also creates another failure mode: deleting or disabling the KMS key makes the state unreadable. That is why the key gets deletion protection too.</p>

<p>Versioning is the recovery path. If a bad apply or manual command overwrites state, an earlier object version is still available. State locking prevents concurrent writers; versioning helps after a bad write. I want both.</p>

<h2>Read access is secret access</h2>

<p>The most common mistake I see after moving state to S3 is a policy that gives the whole engineering team <code>s3:GetObject</code> on the bucket.</p>

<p>Remote doesn't mean secure. It only means the file moved.</p>

<p>My production CI role gets access to one state path, its lock file, and the matching KMS key. It does not get access to every application's state. A simplified S3 policy looks like this:</p>

<pre><code class="language-json">{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "s3:ListBucket",
      "Resource": "arn:aws:s3:::example-terraform-state",
      "Condition": {
        "StringLike": {
          "s3:prefix": ["payments/production/*"]
        }
      }
    },
    {
      "Effect": "Allow",
      "Action": ["s3:GetObject", "s3:PutObject"],
      "Resource": [
        "arn:aws:s3:::example-terraform-state/payments/production/terraform.tfstate",
        "arn:aws:s3:::example-terraform-state/payments/production/terraform.tfstate.tflock"
      ]
    },
    {
      "Effect": "Allow",
      "Action": "s3:DeleteObject",
      "Resource": "arn:aws:s3:::example-terraform-state/payments/production/terraform.tfstate.tflock"
    }
  ]
}</code></pre>

<p>The role also needs narrowly scoped <code>kms:Encrypt</code>, <code>kms:Decrypt</code>, <code>kms:GenerateDataKey</code>, and <code>kms:DescribeKey</code> permissions on the state key.</p>

<p>Notice that the policy can delete the lock file, but not the state object. Normal Terraform runs need to release locks. They do not need permission to delete production state.</p>

<p>I keep human write access out of the normal path. CI assumes the deployment role through short-lived credentials. A break-glass role can recover old versions, but that role isn't attached to anyone's everyday AWS session.</p>

<h2>Separate environments by access boundary</h2>

<p>I don't put development and production in the same state just because Terraform workspaces make that convenient.</p>

<p>Workspaces separate state snapshots. They do not create separate IAM boundaries. If the same role can read the backend, a developer who needs development state may also be one policy mistake away from production state.</p>

<p>For small systems, separate prefixes plus precise IAM policies can be enough. For higher-risk systems, I use separate buckets or AWS accounts. The useful rule is simple: if two environments need different people or roles, give them different backend access boundaries.</p>

<p>I also avoid using <code>terraform_remote_state</code> as a general-purpose data API. A configuration may expose only selected outputs, but the caller's backend credentials can still read the full state snapshot. If another stack needs a VPC ID, I would rather publish that ID to SSM Parameter Store than grant access to the VPC's entire state.</p>

<h2>Keep new secrets out of state</h2>

<p>Protecting the backend matters, but the best secret in state is the one that was never written there.</p>

<p>My first choice is letting AWS own the credential. For RDS, that can mean setting <code>manage_master_user_password = true</code> so RDS keeps the master password in Secrets Manager instead of passing a password through the normal Terraform argument.</p>

<p>Terraform 1.11 also added write-only resource arguments. The AWS provider supports <code>password_wo</code> on <code>aws_db_instance</code>, for example. Write-only arguments receive a value during the operation and omit it from plan and state files.</p>

<pre><code class="language-hcl">variable "hrr_database_password" {
  type      = string
  sensitive = true
  ephemeral = true
}

resource "aws_db_instance" "hrr_app" {
  identifier          = "app-production"
  username            = "app"
  password_wo         = var.hrr_database_password
  password_wo_version = 1

  # Other RDS settings omitted
}</code></pre>

<p>This needs Terraform 1.11 or newer and a provider resource that supports the write-only argument. The version field is how Terraform knows that the unseen value should be updated.</p>

<p>Ephemeral and write-only values reduce what lands in new snapshots. They don't clean old versions. If a password existed in state before the change, I assume it still exists in S3 version history and rotate it.</p>

<h2>If state leaks, deleting the file is not enough</h2>

<p>A leaked <code>.env</code> file starts a credential rotation. A leaked state file should start the same process, plus an infrastructure review.</p>

<ol>
  <li>Remove public or unauthorized access to the backend.</li>
  <li>Preserve audit evidence instead of blindly deleting everything.</li>
  <li>Rotate every credential that may have appeared in the snapshot or its older versions.</li>
  <li>Review CloudTrail for state object and KMS key access.</li>
  <li>Check CI artifacts, local backups, pull requests, and chat uploads for copies.</li>
  <li>Move supported secrets to managed, ephemeral, or write-only paths.</li>
</ol>

<p>Deleting the current S3 object does not revoke a database password. Rewriting Git history does not revoke an IAM access key. Cleanup matters, but rotation closes the door.</p>

<h2>The checklist I use before the first production apply</h2>

<ul>
  <li>Remote backend dedicated to Terraform state</li>
  <li>S3 Versioning enabled</li>
  <li>Native S3 locking enabled with <code>use_lockfile = true</code></li>
  <li>Public access blocked and TLS enforced by bucket policy</li>
  <li>SSE-KMS enabled with deletion protection on the key</li>
  <li>Separate backend paths and roles per environment</li>
  <li>CI using short-lived credentials, not stored access keys</li>
  <li>No state files or saved plans in Git and CI artifacts</li>
  <li>Secrets Manager, managed passwords, or write-only arguments used where supported</li>
  <li>CloudTrail available for S3 and KMS investigations</li>
</ul>

<p>Terraform state is not a cache and it is not harmless deployment metadata. It is part of the production control plane. I secure it like a secrets store, back it up like a database, and restrict writes like a deployment system.</p>

<p>The <code>.env</code> file still belongs in <code>.gitignore</code>. Add <code>*.tfstate*</code> while you're there, then make sure the real state lives somewhere worthy of what is inside it.</p>
